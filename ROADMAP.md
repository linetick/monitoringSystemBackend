# Дорожная карта по доработке monitoringSystemBackend

## Основание

Документ составлен на основе:

- текущего кода backend;
- ТЗ из сообщения;
- спецификации `Specification API_v2.pdf`.

## Текущее состояние проекта

Что уже есть в коде:

- JWT-логин через `POST /token`;
- получение метрик через `GET /metrics`;
- список процессов через `GET /processes`;
- базовое управление процессами через `POST /processes/{pid}`;
- создание, просмотр и удаление пользователей;
- базовый журнал аудита через `GET /audit`.

Что не доведено до требований:

- авторизация реализована частично и не полностью совпадает со спецификацией;
- нет `PUT /users/{user_id}`;
- нет `GET /audit/export`;
- нет `POST /auth/logout`;
- `/users/me` не совпадает со спецификацией `/auth/me`;
- роли пока сведены к `is_admin`, а не к явной модели ролей;
- смена приоритета процесса реализована некорректно;
- аудит пишется не для всех обязательных действий;
- нет миграций БД и нормального управления схемой;
- в проекте есть небезопасные стартовые настройки: захардкоженный `SECRET_KEY` и дефолтный `admin / 123`.

## План по дням

### День 1. Приведение модели данных и API-контракта

Цель: убрать расхождения между кодом и ТЗ, подготовить базу под дальнейшие доработки.

Задачи:

- зафиксировать итоговый API-контракт по спецификации;
- заменить `is_admin` на понятную ролевую модель: `admin` / `limited`;
- обновить `Pydantic`-схемы ответов и запросов под поля `login`/`role`, если именно такой контракт нужен фронту;
- добавить миграции через Alembic вместо `create_all()` на старте;
- убрать дефолтный `SECRET_KEY` из кода;
- убрать создание администратора с паролем `123`, заменить на безопасную инициализацию через переменные окружения;
- описать ограничения доступа для admin и limited user.

Результат дня:

- согласованная модель пользователей и ролей;
- подготовленная схема БД;
- проект готов к безопасной доработке функционала.

### День 2. Авторизация и сессии

Цель: закрыть требования по авторизации и привести поведение к спецификации.

Задачи:

- проверить и доработать `POST /token`;
- добавить `GET /auth/me`;
- добавить `POST /auth/logout`;
- унифицировать зависимости проверки токена и ролей;
- привести ошибки `401/403` к единому формату;
- залогировать вход и выход пользователя в аудит;
- при необходимости оставить `/users/me` как совместимый alias или удалить его после согласования.

Результат дня:

- полностью рабочая авторизация;
- понятная модель доступа;
- логирование входа/выхода пользователя.

### День 3. Метрики сервера

Цель: довести `GET /metrics` до требований ТЗ.

Задачи:

- проверить, что метрики снимаются именно с нужного сервера, а не только из контейнера;
- вернуть все обязательные поля:
  - загрузка CPU в процентах;
  - использование памяти в процентах;
  - использование диска в процентах;
  - время последнего обновления;
  - имя сервера;
  - статус системы;
  - активные предупреждения/алерты;
- перевести `last_update` в нормальный формат даты/времени;
- вынести пороги алертов в конфиг;
- определить правила расчета `status`: `ok`, `warning`, `critical`.

Результат дня:

- endpoint метрик соответствует ТЗ;
- структура ответа стабильна и пригодна для фронта.

### День 4. Таблица процессов для авторизованных пользователей

Цель: довести список процессов до рабочего состояния для admin и limited user.

Задачи:

- доработать `GET /processes`;
- обеспечить фильтрацию по имени процесса;
- обеспечить сортировку по любому столбцу:
  - `pid`;
  - `name`;
  - `cpu`;
  - `mem`;
  - `status`;
  - `owner`;
- добавить направление сортировки `asc/desc`;
- обработать `AccessDenied`, `ZombieProcess`, `NoSuchProcess`;
- проверить корректность сбора CPU и MEM по процессам;
- при необходимости добавить пагинацию, если список процессов большой.

Результат дня:

- стабильная и пригодная для UI таблица процессов;
- корректное поведение для ограниченных пользователей и админов.

### День 5. Управление процессами для администратора

Цель: закрыть админский функционал по управлению процессами.

Задачи:

- доработать `POST /processes/{pid}`;
- реализовать корректное завершение процесса;
- реализовать корректное завершение дерева процессов;
- реализовать реальную смену приоритета целевого процесса в диапазоне `-20..19`;
- проверить права контейнера и ОС для этих операций;
- оставить обязательное подтверждение `confirm=true` на все действия;
- добавить аудит успешных и неуспешных операций;
- вернуть понятные сообщения об ошибках: процесс не найден, недостаточно прав, некорректный приоритет.

Результат дня:

- админ может безопасно управлять процессами;
- все действия подтверждаются и журналируются.

### День 6. Управление пользователями

Цель: довести CRUD пользователей до требований ТЗ.

Задачи:

- проверить и доработать `POST /users`;
- проверить и доработать `GET /users`;
- добавить `PUT /users/{user_id}`;
- проверить `DELETE /users/{user_id}`;
- добавить валидацию уникальности логина;
- добавить редактирование пароля и роли;
- запретить удаление самого себя;
- залогировать создание, изменение и удаление пользователей;
- проверить, что limited user не имеет доступа к admin-endpoint'ам.

Результат дня:

- полный админский CRUD пользователей;
- роли и права работают предсказуемо.

### День 7. Журнал аудита, экспорт и приемка

Цель: завершить обязательный функционал и подготовить backend к сдаче.

Задачи:

- доработать `GET /audit`;
- добавить фильтрацию и лимиты при необходимости;
- добавить `GET /audit/export`;
- реализовать экспорт минимум в `CSV`, при необходимости также в `JSON`;
- убедиться, что в аудит попадают:
  - логин;
  - логаут;
  - действия с пользователями;
  - действия с процессами;
  - неуспешные админские попытки;
- провести smoke-тест основных сценариев;
- проверить OpenAPI/Swagger;
- обновить краткую документацию по запуску и тестированию.

Результат дня:

- аудит соответствует ТЗ;
- есть экспорт журнала;
- backend готов к интеграции с frontend и демонстрации.

## Риски и технические замечания

- Сейчас проект не содержит тестов. Даже для учебной сдачи стоит добавить хотя бы базовые интеграционные проверки.
- Работа с процессами зависит от прав контейнера и хоста. Это нужно проверить отдельно на целевом окружении.
- Метрики и список процессов в Docker могут отличаться от ожидаемой картины сервера, если доступ к host namespace настроен не полностью.
- Без миграций дальнейшие изменения схемы БД будут рискованными.
